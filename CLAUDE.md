# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is Trinocular?

A web-based SQL query IDE for the Trino distributed query engine. Users write SQL in a Monaco editor, execute queries against Trino clusters via a server-side proxy, and browse results in a virtualized table with a detail inspector.

## Commands

```bash
bun install              # Install dependencies (bun workspaces; packages/* are symlinked)
bun run dev              # Dev server on port 5173
bun run build            # Production build (SvelteKit node adapter)
bun run check            # Type-check with svelte-check
bun run preview          # Preview production build
bun run format           # Prettier over the tree (format:check only reports)
bun run test             # bun's own runner over src/**/*.test.ts
```

Tests are `bun test`, with no framework installed: the store contracts (`stores/fileStore.test.ts` and `stores/sessionStore.test.ts` each run one suite against every implementation), and the save queue (`workspaceSaver.test.ts`, against a store whose promises the test settles by hand). The Valkey suites run only with `TRINOCULAR_TEST_VALKEY=host:port` naming a server to run against (`docker run --rm -p 6399:6379 valkey/valkey` will do) and are skipped otherwise, each run under a key prefix of its own; the `test` job in `.github/workflows/docker.yml` provides one as a service container, so in CI nothing is skipped, and `build` waits on it. A module under test must not import `$env/dynamic/private`, which only vite resolves, and `bun test` does not resolve `$lib` either — so the store implementations take plain options (a logger included, which is why the Valkey stores are handed a `Log` rather than importing one), import their interface `type`-only or by relative path, and `fileStore.ts`/`sessionStore.ts` (which read the config) are the factories nothing tests.

## The README

`README.md` is what a user reads, and this file is what you read; the two describe the same program and go out of date separately. **Keep the README current as part of the change that makes it stale** — not afterwards, and not when somebody notices.

Three things in it track the code and nothing tells you when they drift:

- **The feature list.** It is deliberately free of implementation words — no Monaco, no virtual scrolling, no OIDC — because it answers "what can I do with this", which is the one question the rest of this file never asks. A feature that a user would choose the program for belongs there, phrased as the thing they can now do.
- **The configuration reference.** Every option in `ConfigSchema` (`src/lib/server/config.ts`) is documented there with its default, and every environment variable the server reads (`TRINOCULAR_CONFIG`, `ORIGIN`, `LOG_LEVEL`, `PORT`/`HOST`). So a new field, a changed default, or a new `authn`/`authz`/connection option is not finished until its row is there — a config reference that is merely mostly right is worse than none, because the option it omits reads as one that does not exist. Defaults are the part that rots silently: they are written in the schema and in the code that consumes it (the session cookie's `secure` is derived from `ORIGIN` in `hooks.server.ts`, not in the schema), so check both.
- **The run instructions.** Ports, `bun run` scripts, the image name, the tags it is published under and the Docker build targets, all of which live in `package.json`, `Dockerfile` and `.github/workflows/docker.yml`.

## Architecture

### Client-side data flow

```
Monaco Editor → runStatement() → Trino client (fetch, one per run) → server proxy → Trino cluster
                                          ↓
                              Result (State.svelte.ts)
                              keeps chunks as pages (Rows), $state.raw
                                          ↓
                              Result.svelte → Table.svelte (virtual scroll)
                                                ↓ (Selection: rect + lazy getData)
                                          DataViewer.svelte (debounced)
```

- **State management**: Svelte 5 runes on class instances (`Workspace`, `SqlFile`, `Result` in `src/lib/State.svelte.ts`). `Result` fields use `$state.raw()` to avoid deep proxy overhead on large datasets.
- **Rows** (`src/lib/Rows.ts`): a result's rows, kept as the pages Trino sent instead of flattened into one array. `$state.raw` notices a change by reference, so every arriving page has to produce a new value — and doing that by `concat`ing rows copied everything accumulated so far to append one page. A million rows over a thousand pages spent ~2.4s copying on the main thread, and ~9s if the cluster sent four thousand smaller pages, so the cost got worse the less control you had over it. `append` copies the *outer* array instead — one pointer per page, not per row — which is the same work in ~1ms, and never copies a row, which also halves peak memory (the old code held both the previous flat array and its replacement at each append). `Rows` **must** stay immutable: `append` returning a new instance is what changes the reference, and mutating in place would leave the table silently frozen mid-query with nothing wrong in the code that reads it. The alternative was a mutable array plus a separate `rowCount` rune to carry the notification, which is fewer lines but splits "the rows" from "the fact that they changed" and obliges every reader to know both. Consumers only ever ask for `length`, `slice` and iteration — that is `RowSource` in `table/types.ts`, which a plain `any[][]` also satisfies, so `Table` stays a general component and never learns that results arrive in pages. `slice` is the one place with a real algorithm: a binary search over per-page start offsets, then a walk across page boundaries.
- **Files**: `Workspace` holds `SqlFile`s (name + content + `viewFormats`), persisted through a `WorkspaceStore` (`src/lib/workspaceStore.ts`): `LocalWorkspaceStore` in `fileStorage.ts` is this browser's `localStorage`, `RemoteWorkspaceStore` is the server's file store behind `/api/workspace`, and `+page.ts` picks one from the `fileStorage` flag in layout data and *loads it before the page renders*, so `Workspace` is still built synchronously from a list that is already there. Results are session-only — nothing about a run is written down. `#record()` re-maps each file field by hand, so a new `SqlFile` field has to be added there too or it silently will not survive a reload. The record types and the lenient parse (`toStoredFile`) are `workspaceRecord.ts`, shared with the server, which is why nothing in there touches the DOM.

  **Every write carries the version it expects** (`put(file, expected)`, null for a document being created), and a conflict is an *outcome* carrying what the store holds now, not an exception. `WorkspaceSaver` (`workspaceSaver.ts`) is the queue between `persist()` and the store: it diffs every document against what it last wrote or read (seeded from what was loaded, which is the part that matters — a tab that has not touched a document never writes it), keeps one request in flight per document and sends a change that lands meanwhile once the first returns, retries a failed save with backoff while `Workspace.saveFailed` puts `Not saved` in the document header, and drops a *refused* one (quota, the server's size cap) after reporting it, since asking again would not change the answer. Whose copy wins a conflict is the rule other tabs' writes already follow: the active document is this tab's — it is sent again against the version that beat it, and created afresh if that version was a removal — and any other document takes the store's copy. A removal waits for the document's in-flight save, or the DELETE could overtake the PUT and leave the document back on the store. `flush()` (from `pagehide` in `Application.svelte`) sends what the debounce was holding with `keepalive`, which the browser honours only under ~64KB.

  **One key per file** (`…:file:<fileId>`), plus an advisory `…:ui` holding the active file, the listing order and the connection. It was one key holding every document, which made three unrelated failures share one fate: a parse error lost the whole workspace rather than one file, a quota rejection stopped every document persisting rather than the one that overran, and two tabs each rewrote the entire list from the copy they loaded, so whichever saved last silently reverted the other's work on files it had never opened. The file keys are the truth and `:ui` is only a hint — ids in it that name nothing are dropped, files it omits sort in by name — so the two cannot disagree in a way that needs repairing. `persist()` compares each file against what this tab last wrote (seeded from what it *loaded*, which is the part that matters) and writes only what changed: a tab that has not touched a document never writes its key, so it cannot put back a stale copy. A refused write is reported rather than swallowed, and now costs only the file that caused it.

  **Other tabs** are followed through `WorkspaceStore.watch` (`Workspace.watchStore`, mounted from an `$effect` in `Application.svelte`): the local store's is the `storage` event, which fires only in the tabs that did not write; the remote store's is a `BroadcastChannel` posted after each successful write, for the tabs of this browser, plus a re-read of the listing on `visibilitychange` and on a slow tick while visible, for other browsers — a version that moved is reported as a write, an id that is gone as a removal, and a document whose removal this tab has asked for and not yet heard back on is skipped, or the refresh would announce it as new. On every `load` the remote store also imports what localStorage holds that the server lacks and then *removes the local copy*, so that localStorage only ever holds what has never reached the server: that is what lets the check run on every visit (a file made during a spell back on `browser` storage is picked up) without a file deleted on the server coming back from its stale local copy. A once-per-browser marker was the first design and stranded exactly that file. The rules for applying what arrives follow from where a document's text lives: `Editor.svelte` builds a monaco model from `SqlFile.content` once and caches it in a WeakMap keyed by the `SqlFile`, after which the model is the truth and writing to `content` would not reach the screen. So the file open in this tab is never touched — its text is under somebody's caret — while any other file whose text changed is *replaced* with a new `SqlFile` rather than mutated, since a new WeakMap key is what guarantees the stale model is dropped and a fresh one built on next open (its results go too; they belong to statements that no longer exist). Names and connections are applied in place, being nothing monaco holds.
- **Connection is per workspace**, not per file: `Workspace.connectionId` is one rune deciding which cluster every document's statements run against and which cluster the data browser shows, chosen from the `Dropdown` in the data browser's rail (`SchemaBrowser.svelte`) and stored in the `:ui` record beside the active file. It was per file once, with the chip in the document header — which meant switching files could switch clusters under a browser tree that still showed the old one, and the connection had to be repeated in the switcher and the browser to be findable at all. A stored `connectionId` the config no longer declares is healed back to the default on load (`#knownConnection`) — an id the config does not know can only 404 at the proxy — and `persist()` then writes the healed value back. `Workspace.catalogFor(id)` hands back one `CatalogCache` per connection, kept for the session — browsing a Trino cluster is slow enough that throwing the tree away on a switch is felt, so switching away and back finds it as you left it. They are all built in the constructor rather than on first use, which is a correctness requirement and not an optimisation: a `CatalogCache` is made of runes, and a lazily-built one was built inside whichever `$derived` or `$effect` asked for it first, whose read of it then tracked nothing (see the convention below). Switching a document to another cluster left the schema browser empty, root and all, until you switched away and back. Runs still build a fresh `Trino` client each time, since the client carries mutable session header state. With **no connections at all** every id heals to `""`, a proxy path that can only 404, and the browser used to open on exactly that — `Could not list catalogs: HTTP error 404` — which reads as something broken rather than something missing. `Workspace.hasConnections` is the one fact, and the four places that would otherwise ask the cluster consult it: the schema browser skips the fetch and shows `NO_CONNECTIONS` (a hint, not an error), the browser's connection menu says so in a disabled row instead of opening empty, `run()` settles the result through `Result.fail` with the same text before any request is made, and completion is handed `NOTHING_TO_DESCRIBE` so a popup does not 404 behind the scenes. The `""` cache is still built, so every lookup stays total; it is simply never asked.
- **Result ↔ statement association**: results belong strictly to Monaco range anchors (`Result.anchorId`), not SQL strings. Multiple identical statements in a file remain completely independent. Erasing a statement collapses its anchor and drops its result: cutting a statement loses its result, and pasting it back — anywhere — starts from an empty strip. (Reclaiming a result by matching a pasted statement's text against the erased one was tried and removed; it was the one rule here that could guess wrong, since two identical statements could swap results.) Re-running replaces only that specific statement's result, and a result that is dropped (statement erased, re-run, evicted, file deleted) is stopped via `Result.discard()` rather than left polling. The anchor decorations are `NeverGrowsWhenTypingAtEdges`: on monaco's default stickiness an insert at either edge extends the decoration, so typing a new statement below a finished one grew that one's anchor across both and the new statement came up already showing its neighbour's result.
- **Statement toolbar** (`Editor.svelte`): the `▶ Run / ☰ Results / ✕ Cancel` strip above each statement is a monaco *content widget* over a view zone, built by the component itself — not a `CodeLensProvider`. Monaco puts two chained 250ms+ debounces in front of code lens provide and resolve with no public flush, so a running query's state reached the lens a third of a second late; owning the DOM makes a state change a `textContent` write. `syncToolbars()` reuses one strip per statement, re-anchors them on every edit (a content widget only refreshes its cached model position when laid out), and hands the buttons straight to the `onexecutesql` / `onshowresult` / `oncancelresult` props. Cancel (`Result.cancel()` → `DELETE /v1/query/{id}`) is reported back by Trino as a `USER_CANCELED` error, so failed and cancelled results share the `.status.failed` styling, with the Trino error name in the tooltip. A failed statement reads `Error` behind a warning triangle rather than offering rows it does not have, and `Details` is a plain `<a href>` to the `infoUri` Trino reports for the query — the proxy deliberately does not rewrite that one, so it points at the cluster's own UI. The icons are `@lucide/svelte` components `mount()`ed into that hand-built DOM, and the stylesheet has to give them `max-width: none`: a content widget with `allowEditorOverflow: false` is capped at the editor's content width, read once when the widget is added, which is 0 for the strips built before the editor's first layout — an ancestor `max-width: 0` that nowrap label text overflows harmlessly but that collapsed the icons, which is why a fresh strip used to read `Run` with nothing beside it.
- **Query progress** (`QueryProgress.svelte`): what the results pane shows while a query has no rows yet, replacing the spinner; once rows stream in it shrinks to a one-line strip above the table (`compact`). It deliberately never shows Trino's `progressPercentage`. That figure's denominator is the splits discovered so far, and measuring against it on a real cluster gives 0.0% for five seconds then 13.3% then 100%, or 20.7% held for eighteen of twenty-one seconds — the number is not wrong so much as meaningless. Everything drawn is a count Trino reported or a composition of counts: the wide bar is *composition* (how the currently known splits divide into completed/running/queued), never completion, and the total is labelled "known so far". Splits alone are not enough either — a `tpch.sf10.lineitem` scan sits at 0/30 completed for its whole run — so the history is two charts on one time axis: split counts stacked, and rows processed. The splits y-scale is the largest total seen, so discovering more splits rescales the stack and the goalpost moving is drawn rather than hidden. Stage bars share one x-scale so their widths compare. `Result.progress` (`State.svelte.ts`) is the series behind the charts: one sample per stats change, thinned to an interval that doubles when the 240-sample cap is hit, so an hour-long query keeps its shape at half resolution rather than losing its beginning. Note `processedRows` counts a row at every stage it passes through and is restated as raw input rows on the settling chunk, so it can *drop* when the query finishes — hence "processed", which stays true either way.
- **Row limit** (`Result.limit`, `Workspace.rowLimit` / `limitRows`): a run shows `DEFAULT_ROW_LIMIT` (1,000) rows, or the number typed into the results rail, and then pauses to ask; the toggle and the number are session state only. It is deliberately not a `LIMIT` in the SQL, which would make "fetch more" a re-run. Trino sends results as ~1MB pages with no row-count or page-size knob on the request (the old `maxWait`/`targetResultSize` params were removed in 2025), so the cap is applied by the client between pages: `#take` appends a page cut at the cap and keeps the tail in `#pending`, and `execute` then simply stops asking for the next page — the loop is pull-based, so the hold is the absence of a request. It holds only once a page has actually been cut, not the moment the count reaches the cap: Trino sends stats-only chunks with a `nextUri` right up to the end, so a query of exactly the cap would otherwise claim more rows and hold for nothing, while for a query with more the next page settles it either way (at the price of one page, ~1MB, fetched into `#pending` before the banner shows). What has to be arranged is that the cluster does not read that silence as a client that went away: Trino fails a query as `ABANDONED_QUERY` after `query.client.timeout` (five minutes by default), and a `HEAD` on the current `nextUri` resets that clock without consuming the page, which is what the official clients send every 30s while their caller is slow. `Trino.heartbeat` sends one every `HEARTBEAT_MS`, and the proxy has an explicit `HEAD` handler because a HEAD's answer carries a JSON content-type and no body, which the GET path's `json()` would choke on. A held query is not free — it keeps its memory reservation and its resource-group slot on the cluster while backpressure stalls it — so a hold is stopped after `MAX_HOLD_MS` (ten minutes), and `stopped` says why. `stop` (also what `cancel` and `discard` do while held) sends the ordinary cancel and settles the result locally through `stopped`, because nobody is polling to receive the `USER_CANCELED` chunk that settles every other cancel; a stopped result keeps its rows and a green dot, since it is a finished truncation rather than a failure. `fetchMore` raises the cap by the step the run started with and `fetchAll` clears it; either resolves the hold, after which `execute` takes from the tail first and only then asks for another page, in a loop, since the tail can exceed one step. Partial cancel (`partialCancelUri`, which kills the leaf stage and drains to a clean `FINISHED`) was considered for the cap and rejected: the rows are gone after it, so "fetch more" would be a re-run, and the drain brings back everything buffered — up to 64MB — well past the cap. Trino never reports how many rows remain, so the banner says more exist and not how many.
- **Rows are released** (`Result.release`, `Workspace.#releaseRows`, `ROW_BUDGET`): the workspace keeps at most `ROW_BUDGET` (500,000) rows for results nobody is looking at, and past that the largest results let their rows go (oldest first between equals) — keeping their columns, stats and error, so the run still reads as what it was, the rail keeps the count it had, and the pane says how many rows it gave up and to run the statement again. Before this, ten results a file, every file, for the session, with "fetch all" among them, was how a tab came to hold a few million rows nobody was looking at. It is a budget of *rows* and not of results because twenty small queries in one file cost nothing and should all stay, while one "fetch all" is the thing that needs reclaiming. It is applied when a run starts and again when it settles — a result's size is only known at the end, and the end is when it can push the total over — and `release` declines the result on screen, a running one (still being filled) and a held one (still answering for a query on the cluster), which is why the total can exceed the budget: the budget bounds what is kept *beyond* what is in use. A released result cannot be saved.
- **Trino client** (`src/lib/trino/index.ts`): Async iterator over paginated Trino REST API responses. Manages Trino session headers (catalog, schema, prepared statements) across requests. One `Trino` instance per query — not safe for concurrent use, because each response can rewrite those headers and two queries sharing an instance would rewrite each other's session. It is a fork of the `trino-client` npm package with everything that assumed a direct connection to a cluster taken back out: there is no auth, no `X-Trino-User`, no extra credentials and no TLS options, because the browser talks only to this app's own proxy and the proxy is what attaches identity. Anything added back here has to be added to the proxy's forwarded-header list before it will travel.
- **Type conversion** (`src/lib/trino/table.ts`): Converts Trino `TypeSignature` → table `Field`/`DataType`. Handles nested rows, arrays, maps and binary (base64→Uint8Array). A map is `Dictionary` (`{key, value}` DataTypes, beside `Struct` and `List`): Trino sends one as a JSON object with its keys already strings, so conversion, export (`toJson`) and the inspector all keep the keys and recurse into the *value* type — which is what gets a `row` inside a `map` its field names back in an ndjson file. Before it had a DataType of its own it fell through to `"string"`, and the table drew `[object Object]`.
- **Type *strings*** (`src/lib/trino/typeString.ts`): the other direction onto the same types, and deliberately separate from `table.ts`. `table.ts` walks a `TypeSignature`, the structure Trino attaches to query *results*; the catalog only ever reports a rendered string (`row("a" integer, "b" array(varchar))`), and recovering the structure by re-asking the engine would be a query per column. So this parses the string: `typeChildren` (a row's fields, a map's key/value; an array unwraps to its *element's* children so `array(row(...))` expands straight to the row's fields rather than through a level that says nothing), `typeCategory` (which icon), `abbreviateType` (`row`). The shapes it handles were read off the engine, not assumed: named row fields are always quoted and `""` escapes a quote, anonymous ones are bare types (shown as `[1]`, `[2]`, which is how you subscript them), field names contain dots and spaces, and `timestamp(6) with time zone` puts words *after* the parameter list.
- **Table** (`src/lib/components/table/`): Virtual-scrolling table rendering only visible rows. Selection is a lightweight rect; `getData()` lazily extracts and converts cell values. Rows are 30px, the header is a 36px rail carrying the column name on one line, with its type as the same icon the schema browser uses for that category (`TypeIcon.svelte`, shared by both) — spelled out, a type is mostly noise a column at a time and it took a second line of header away from the name, while the icon is a vocabulary you have already learned from the drawer and costs one glyph of width. The name leads and the icon is pushed to the far edge of the cell, so the icons line up down the right of the header whatever the names do; a numeric column's name sits up against its icon instead, following the right-aligned figures below it. The wording is on hover: the icon's title is the type abbreviated the way the tree abbreviates it (`row`, not `row(...)`), the name's is the untruncated name. Body cells have horizontal hairlines only: the vertical rules made every cell a box, and column tracking is carried instead by the header separators, the row-number gutter, and right alignment plus tabular figures on numeric columns (every numeric Trino type maps to the `"integer"` DataType, so that is the test).

  **Column widths** are two layers. `measured` is each column's content width — the header name plus the widest cell among the first `SAMPLE_ROWS` (200) rows, measured with canvas `measureText` in the container's font rather than by laying anything out, clamped to `[50, 400]`. It is taken once the first rows land (from the header alone before that) and never again for that result: a later page re-measuring would move the columns under a reader mid-stream, and one page is a sample of the rest. Digits in a numeric column are measured as zeros, since the cells draw tabular figures and a canvas cannot be asked for them. `layout` then fills the container: when the measured widths sum to less than it, the slack is shared out in proportion, so a three-column result reads as a table and not three strips against the left edge, and a pane or window resize re-fills through `bind:clientWidth`. Dragging a header edge writes `pinned[i]`, which stands in for the measured width *and takes no share of the slack* — that is what lets the dragged column land where the pointer leaves it while the others go on filling; the naive "stretch everything after the drag" slid the column away from the pointer. A second press on the same handle within 400ms fits the column to its content over the loaded rows (`FIT_ROWS`, capped at `FIT_MAX_WIDTH`), detected in `pointerdown` because that handler's `preventDefault` suppresses `dblclick`. The trailing spacer column and its 100px minimum are only for when nothing flexes — every column pinned, or the total already past the container. `CELL_PADDING` counts the header's 1px rule and a pixel for rounding on top of the 12px a side; at 24 every header name came up one pixel short and ellipsised.
- **Saving a result** (`src/lib/export.ts`): `Save` in the results rail writes the rows the browser is already holding — re-running the query server-side to render a file would be a second snapshot of a moving table, a second cost, and a second thing that can fail. It serializes the values Trino *sent*, not the converted ones the table draws: conversion exists to put a value on screen (varbinary becomes a `Uint8Array` so a cell can show bytes) and every one of those decisions is the wrong one in a file, where base64 is what arrived and what a reader expects back. A row, an array, a map — anything with an inside — becomes JSON in the cell, and since Trino sends a row as a bare array of values the field names are put back from the type, so it reads `{"a":1}` rather than `[1]`; `JSON.stringify` with no indent emits no newline of its own, so a nested value never breaks the line it sits on. A cell that would open as a formula in a spreadsheet (`=`, `+`, `-`, `@`, tab) gets a leading apostrophe, since Excel, LibreOffice and Sheets all *evaluate* such a cell and the row may have been written by someone other than whoever exports it; quoting is not the defence, because a spreadsheet strips the quotes and evaluates what is inside. Numbers are exempt by shape (`-3`, `+1.5e9`), or every negative figure in the file would turn into text — which would be a worse file than the one the escape was protecting. The formats are `EXPORT_FORMATS`, which is what the menu is drawn from, so another one is a serializer and a list entry and nothing in the UI. CSV and **ndjson**: ndjson is where a row keeps its shape — object, array, all the way down — while CSV has one dimension and has to spend a quoted JSON string on anything that has two. (Two columns of the same name collapse into one key there; Trino allows that and JSON does not, so CSV is the format that can carry it.) The chip is a `Dropdown` (below), so it opens and dismisses exactly like the document header's and the data browser's.

  **Copying a selection** (`clipboardText`, same module) is the same serialization on the clipboard, and not a chord of its own: `Table` answers the browser's `copy` event, so ⌘C, the Edit menu and the context menu all land on the one handler, and the table stays out of it when it has no selection. The listener is on the *document*, gated on the grid container being `document.activeElement`, and not on the container itself: Chromium fires `copy` at the focused element, but Firefox fires it at the text selection's node — `<body>` when there is none — unless the focused element is editable, and the grid makes no text selection by design. A handler on the container was never reached in Firefox, so ⌘C silently copied nothing there. `Table` hands the handler the *raw* rows through a `clipboardText` prop rather than serializing itself — it does not know what a Trino value is — and `Result.svelte` passes the function from `export.ts`. One cell copies as the value and nothing else (no quoting, no formula apostrophe — a cell is copied to be pasted as itself; a row, map or array the cell abbreviates copies as its JSON), and anything larger copies as CSV rows without the header line, since the header was not selected and a block pasted beside other data should not bring a title row with it.
- **Split pane layout**: Three-pane UI (schema browser | document | inspector) using `SplitPane` (`src/lib/components/split-pane/`), written from scratch for this repo — the previous one was a port of a package that carries no license, which is not something an open repository can ship. It takes *N* panes as an array of snippets (`panes`) and a bindable `layout` beside it, one `{size, min?, max?}` per pane, and draws a divider between each neighbouring pair. The sizes are weights — `flex-grow` from a zero basis, so the panes fill exactly what the dividers leave and the numbers need not sum to anything, though writing them to 100 makes them read as percentages — and `min`/`max` are a percentage or a pixel count set straight onto the pane as CSS min/max size, so a pixel bound holds through a window resize with no observer. A divider moves width between its two neighbours and nobody else: it was two nested two-pane splits before, and the inner one's position being a fraction of its container meant dragging the browser's edge also resized the inspector. Each divider is a 1px rule that is also a focusable `role="separator"`: it drags under pointer capture (no `window` listeners, no catch-all overlay) and takes the arrow keys, `Shift` for a bigger step, and `Home`/`End`. The bounds are applied in JS as well as CSS, since `layout` is bindable and must never report a size outside its own range. The `{#each}` is keyed on the snippet, so a pane's DOM survives a resize. Each pane owns a 36px `.rail` at its top edge, which is what makes the three headers line up as one band across the window without any of them knowing about the others; the top bar (below) sits above that band. The inspector is always on screen: it was closable once, and with no button and no chord left to reopen it, a pane you can drag shut is a trap rather than a layout, so it and the document each carry a `min`.
- **Inspector** (`DataViewer.svelte`): reads whatever the table has selected, at full window height, as one *document per selected row* — field/value pairs with structs, maps and arrays flattened to dotted paths (`attrs.color` for a map entry, the same spelling as a row field), headed by the row number the table shows so a value traces back to its row. It is a pane of the window rather than a region of the results, which is what lets the whole selection be readable at once and would let it serve a document type other than a SQL file. It has no toggle: no chip in the results rail, no close button in its own rail, and no `⌘I` — which had been registered both as a monaco action and on `window`, for the same reason `⌘P` still is. `⌘P` is now the only chord that needs that treatment.

  **Full window** is the same component a second time, inside `Dialog.svelte` — a native `<dialog>` under `showModal()`, so Escape, the backdrop click, the focus trap and the return of focus to the grid on close are all the platform's, the way the menus' dismissal is. `Application.svelte` renders one `viewer` snippet in both the pane and the dialog, with `expanded` telling the component which it is; the rail draws `Maximize2` for `onexpand` and `X` for `onclose`. It opens from that chip or from `Enter` on the table's selection (`Table.onopen`), and opening first collapses the selection to the active cell's whole row (`Table.selectRow`): full window is one whole row at a time, whatever cells were selected. **The table stays mounted behind the dialog and still owns the selection**: the rail's `↑`/`↓` chips and the arrow keys (`Home`/`End` for the ends; `Shift` extends in the pane, never in the dialog) call `onstep`, which `Application` routes to `Result.step` → `Table.step` — the same `move` the grid's own arrow keys use — and the new selection flows back out through the binding as it always did. So stepping in the dialog is stepping in the grid, there is one selection model, and closing the dialog leaves the table scrolled to and selecting the row you ended on. A second selection model in the inspector was the alternative and would have had to be reconciled on close. In the pane the keys are taken only from inside the component (a click on a rail chip leaves focus there); expanded they are the window's, since under a modal there is nothing else they could mean, and the field filter takes focus on open (after `tick()`, so it lands after `showModal()` has done its own focusing). On close, `Application` focuses the table (`Result.focus` → `Table.focus`, which scrolls the selection into view) rather than letting the dialog hand focus back to whatever opened it, which for the chip is the chip. A single-row selection is drawn synchronously: the 100ms debounce on `selection` is for a drag, which changes a block on every mousemove, and applied to stepping it skipped every row pressed faster than it without ever showing it. **Stepping is a diff, not a rebuild**: the outer `{#each documents}` is positional on purpose — keyed on the row number, a step changed every key and tore the whole document down (every field, its value component, its buttons) to build the same columns again, which a Firefox profile put at 200–950ms a key press on a wide row, half of it mounting lucide components and the rest feeding GC pauses of up to 700ms. Positional, the inner list diffs by column path (`entry.id`) and only fields that appeared or vanished are mounted. The per-field `Eye`/`Copy` icons are lucide's paths written out as static markup for the same reason: a lucide component is two components deep with a rest-props object, three deriveds, a spread and an effect per child element, and a spread of any kind (`{...ICON}`) would bring the `attribute_effect` back, so the attributes are literal. And `step` from the dialog passes `reveal: false`, since scrolling a covered grid to the row reads `scrollTop` and forces a layout of the dialog's freshly built document; `focus()` on close scrolls to wherever the stepping ended. Both instances say `Row 12 of 3,500 · 8 fields` (`rowCount` is the result's row count, so the last-row chip knows to disable). **The key column is resizable** the way the table's are: a `Field │ Value` header row styled as the table's `th` carries the separator, and the separator's edge is the one `resize-handle` (pointer capture, the same 6px zone and 400ms double-press-to-fit rule, measuring the longest key on screen through the `textMeasurer` in `src/lib/textWidth.ts` that the table's column sizing shares). The width is `--key` on the component root, clamped to `[MIN_KEY_WIDTH, width − MIN_VALUE_WIDTH]`; expanded it starts at half the width and follows a resize until dragged, in the pane at 150px. Per instance and session-only.
- **Top bar** (`TopBar.svelte`): a band of `--h-rail` above the three panes, on `--s0` rather than the rails' `--s1` so it reads as the page the chrome sits on, set off by a 2px `--line-strong` rule — a shadow and then a fade were tried and both read as one more hairline. It holds the app's own things — the logo — `branding.logo` in the config, rendered with `{@html}` like the message, or the bundled `src/lib/assets/logo.svg` when it is unset, or nothing when it is `""`. The bundled one is imported `?raw` and goes through the same `{@html}` as an operator's, inline rather than an `<img>`, because an image is opaque to page CSS: its paths are `fill="currentColor"` and the pink is `color` on the `.logo` box, one line to retune or make follow the theme (the binoculars are negative space in the disc, so the rail's own surface shows through them either way); it sits in a 20px box that scales an `svg` or `img` child to itself and clips anything else, since CSS outranks an svg's own `width`/`height` attributes — and the app's name beside it at the left (`branding.name` in the config, `Trinocular` by default), `Account.svelte` at the right, and between them `branding.message`, which is the operator's HTML rendered with `{@html}` and centred on the window rather than between its neighbours (a three-column grid with matching outer tracks). The config's `branding` object reaches the browser whole, in layout data. Rendering config HTML unescaped is deliberate: it comes from the same file as the security policy, and the CSP is what stops a script in it, not this component. A footer used to hold the user id, a theme toggle and a logo, and spent a whole band of window height on one string and a button pressed about once; the account chip then spent a while lodged at the end of the inspector's rail, on the strength of that rail's right edge being the window's — but it had nothing to do with the inspector, and its room came out of a pane whose width is the reader's to set. `Account.svelte` is a `Dropdown` whose menu holds the full id, the theme (below), and `Sign out` — until which the only sign-out in the app was on `/auth/forbidden`, so everyone actually allowed in was stuck.
- **How a value is drawn** (`src/lib/viewFormats.ts`): a varchar column holding a JSON document is the case this exists for — the type says `varchar`, the string says `{"`, and only the person reading it knows which of those to believe. So every field in the inspector carries a picker (the eye beside the copy button, revealed on hover) offering `Text` and `JSON`, and the choice is remembered on the **document** — `SqlFile.viewFormats`, persisted with the file — rather than on the result, which the thing you do most would throw away, or on the workspace, where a column called `payload` in one file would silently re-type `payload` in another. It is keyed by the path the inspector shows, `items[3].meta`, indices and all: the same field in another row is the same choice, since that much is a property of the column — and a map entry is keyed the same way (`attrs.payload`), on the bet that the same key in another row holds the same kind of value, even though a key is data rather than schema; there is no `every attrs` group, since a map has no index to drop — but the elements of an array are not each other — a varchar array can carry a JSON document in one element and a sentence in the next, and collapsing the index to `items[]` would make one click re-type the whole array. For an array whose elements *do* agree — two hundred JSON documents in one column — the menu offers the same formats a second time under `every items[]`, which writes the path with its indices dropped; the element's own choice wins over the array's, and choosing for the array clears the elements that were picked out of it, since otherwise `Text` for every element would leave three of them JSON with the menu showing both as chosen. Both groups are headed by the path they write, because a choice that outlives the row it was made in is a surprise only if nothing said so. The collapsed path is built by `flatten` as it walks, not read back out of the display key — the same reason a tree node's kind is not recovered by counting dots — and the one place that does match strings (`underPath`, which sweeps the stored map) turns only the `[]` positions into wildcards. A format is one entry in `VIEW_FORMATS`, the arrangement `EXPORT_FORMATS` already uses, so hex or markdown later is a `render` and a list entry and nothing in the UI; `applies` is what keeps an integer column from being offered JSON, and a field with only one format on offer grows no picker at all. Nothing sniffs: decoding varbinary to text is not a guess, but the old "starts with `{"`, so pretty-print it" rule was exactly the guess an explicit, remembered choice replaces — it was right often enough to be relied on and wrong with no way to say so. A format that cannot be honoured says so on the row (`Not valid JSON`) and shows the value as it arrived, because drawing the raw string silently would make the picker look broken rather than the value. The choice is the inspector's alone: `Copy row`, `Copy selection` and `export.ts` still serialize what Trino sent, and only the per-field copy hands over what the row shows.

  **What a format hands back** is a `Rendered`: the `text` the per-field copy button hands over, and a `view` — a component and its props — that the row mounts with a spread and never looks inside. So the inspector does not know what kinds of value exist, and a new format is a `render`, a component if it needs one, and a list entry. It was a bag of optionals before (`text`, `pre`, `note`, then `html`, then `image`), with the row switching on which was set and the cap function exempting two of them, which is the shape that grows a branch per format. `TextValue.svelte` is what `Text`, `JSON` and every fallback ("Too large to render", "Not valid JSON") mount, and it owns the size cap (below); the inspector adds the field's display key as `title` to whatever it mounts, since a format is not told the key and the frame and the image want it for accessibility.

  **Hex** is `hexdump -C` at eight bytes a line, the width that fits the pane, with the length as the last line the way hexdump prints it. It is offered for strings too, dumped as their UTF-8, since a BOM or a zero-width character is exactly what `Text` cannot show. It mounts `TextValue` with `wrap` off, so a line scrolls sideways rather than folding its columns into each other, and stops at 64 KiB with a note, which is already past what the expanded text cap will draw.

  **HTML, Markdown and Image** are the formats past `Text`, `Hex` and `JSON`. HTML and Markdown (`marked`, a devDependency like everything else that bundles) both land in `HtmlFrame.svelte`: an `<iframe>` with an empty `sandbox` and a `srcdoc`, so the document has no script, no forms, no navigation and an opaque origin — the app's CSP is what says a result cell can never become script, and the browser's own sandbox holds that line without a sanitiser of ours in front of it (sanitising into the pane was the alternative, and it would have left a document's CSS free to paint over the app). The frame inherits the page's CSP, and puts a stricter one of its own in a `<meta>` first in its head — `default-src 'none'`, with only `data:` images and inline styles allowed, since neither is a request. Policies combine, so the meta can only tighten: under the page's policy alone a document could still fetch images and stylesheets from this origin with the session cookie attached (harmless GETs, but a fetch is a fetch), and with the frame's own policy it was measured requesting nothing at all, from either origin, while script files were neither fetched nor run. No page directive had to be loosened; a `srcdoc` frame under `default-src 'self'` was checked in headless Chromium before this was built on. The pane's palette and type are read off `<html>` with `getComputedStyle` and written into the frame as a base stylesheet, since the frame inherits nothing — after `tick()` on a theme change, because the attribute is set by an ancestor's `$effect` and user effects run after render effects, so a `$derived` would read the palette before it landed. The frame is a fixed height with a resize grip rather than sized to its document: nothing sandboxed this tightly can be measured from outside, and a fixed box is also the size cap for these formats. `ImageValue.svelte` draws a varbinary as an `<img>` on a data URL, which is inert (SVG included) and so needs no frame; the media type is sniffed from the magic bytes only so the row can say `PNG · 10 × 10` and so SVG, which is XML and is not sniffed by the browser, gets the type it needs — the browser is the judge of the rest, and its `error` event is what puts `Not an image the browser can draw` on the row. Both components key their per-value state (failed, loaded size) on the value rather than resetting it in an effect, since the row reuses the component when the value under it changes.

  **The size cap** lives in `TextValue.svelte`, because text is the one kind of value whose height on screen is its length: a frame is a fixed box and an image is bounded by the pane, so neither needs one. It cuts what reaches the DOM to `DISPLAY_LIMIT` (4,000 characters) — a single varchar can be megabytes, a selection is a block of them, and the pane lays every row out unvirtualised, so without this one cell decides how long the inspector takes to draw. It caps the screen and not the value: the row says what it is holding back ("Showing 4,000 of 9,000 characters"), `Show more` raises that one cell to `EXPANDED_LIMIT`, and the copy button always hands over the whole thing. Expansion is remembered against the text itself, not reset by an effect: the row list is keyed by field name, so the component survives a change of selection, and a cell that turned out to be worth reading says nothing about the next row's. JSON, HTML and Markdown have a second and larger limit (`FORMAT_LIMIT`) before they will parse or render at all, since formatting half a megabyte to then show four thousand characters of it is work nobody asked for.
- **The three surfaces** each do one job, which is why there is no left-hand accordion any more. `SchemaBrowser.svelte` is the drawer: one full-height tree for the workspace's connection, under a rail holding the connection picker and a filter box (`FilterBox.svelte`; the inspector filters per column instead, in a row under its header — one `.textbox` for field names and one for values, each a case-insensitive regex narrowing only its own column, Escape clearing the box it is in. The value box matches the *rendered* text — `render(...).text`, the same string the per-field copy hands over — so a varbinary shown as text is found by that text and not by its base64; `documents` renders each entry once and the row, the copy button and the filter all read that one `Rendered`. A pattern that will not compile marks its box `aria-invalid` and filters nothing, since matching nothing on a half-typed `(` would empty the pane on every open bracket). Its filter narrows *what is already loaded*; opening a branch and the reload button on its row (right-aligned, shown on hover) are the only things in it that reach the cluster, and each takes a click. Nothing on the keystroke path may call `CatalogCache.load*`, or a cluster with slow connectors would crawl. A `SHOW` the cluster refuses — access denied, a schema dropped since it was listed — does not throw out of the Trino client: the failure arrives as `error` on the last chunk, and until `CatalogCache` checked for it a forbidden catalog opened as an empty one. Now the cache records the message under the same key `loading` uses (`CatalogCache.errors`), the node draws it beneath its row while open, and a failed fetch drops the list it was replacing so the error is never contradicted by rows under it. Reload is `load*(fresh)`: the same fetch with the cached list ignored, for that one list only — after it lands, `SchemaBrowser.loadNode` re-asks for every open branch beneath, which the cache answers for free except where a failure had emptied it, so reloading a parent is also how a child whose fetch failed comes back. A column expands too: its type string already describes the whole shape, so row fields hang under it as child nodes, recursively and without touching the cluster — opening one is a pure display change, and only the catalog/schema/table levels carry a `load`. Because a column's fields sit at no fixed depth, and because a Trino field can be named `weird name.with dot`, the old trick of reading a node's kind back out of its id by counting dots is gone: ids join their segments with a unit separator, and what each node *is* (its icon, and whether it fetches) is recorded in a `meta` map beside the tree, where it is built. Types carry an icon each — braces for row, brackets for array, hash, clock, binary — and an expandable type's own text is abbreviated to `row`, since the full text of a nested row runs to hundreds of characters and would otherwise set the width of the whole pane (the chevron is what says there is more); the untruncated name and type are on the row's `title`. `TreeView` is stateless — the set of open ids is the whole truth and is passed in, so the chevron cannot draw one thing while a click does another. The browser keeps that set per connection (ids collide across clusters). A filter does not decide what is open — you do: a branch is open because you had it open, plus the ancestors holding a match on screen, minus anything clicked shut while the filter is up (`filterOverride`). So filtering never reveals a subtree you had collapsed — it cannot paint three thousand rows you were not already looking at — and whatever you had expanded under a match stays exactly where it was. **A table row's menu** (the `⋯` beside its reload button, shown on hover — lucide's `Ellipsis`, at the tree's 14px icon size rather than the reload's 12, since an ellipsis at 12px was too faint to find) offers `Copy`/`Insert` × `CREATE`/`SELECT`. It is one `Menu` for the whole tree, pointed at by every table row's button, for the reason the inspector's picker is: only one can be open. `TreeView` knows nothing of it — it takes an `actions` snippet per row and handles only the hover reveal, so the browser decides which rows get one (`meta[id].table` holds the name's parts, again rather than re-splitting the id). The CREATE is the cluster's own DDL via `CatalogCache.showCreate` — `SHOW CREATE TABLE`, uncached since one click is one query and a stale copy would have no reload to clear it. `SHOW TABLES` lists views too, and `SHOW CREATE TABLE` refuses one with *"is a view, not a table"* (or *materialized view*), which is matched and followed to `SHOW CREATE VIEW` rather than surfaced. The SELECT is written in the browser from the columns the tree already holds (`selectStatement`, `src/lib/trino/statements.ts`), one per line so the list is there to be cut down, `*` when they are unknown, and the table on its own line under `FROM` at the same indent. Both statements end in `;` — Trino's DDL arrives without one, and `terminated` adds it — so an inserted statement is its own statement to the splitter and gets its own `Run` strip. Names are quoted by `quoteIdentifier` in the grammar package: bare only when lowercase-identifier-shaped *and* not reserved, where "reserved" is a keyword token absent from the grammar's `nonReserved` rule — read off the parser's ATN at runtime, so the list cannot drift from what the parser accepts. `Insert` reaches the editor through `Editor.insert`, exported and called from `Application.svelte` via `bind:this`: at the caret, replacing a selection, set off by a blank line from any text on the caret's line, one undo step. `insert` itself adds no terminator: what it is handed is complete, and where the *previous* statement ends is the file's business. While the statement is on its way the table row draws as loading (`busy` in the browser, merged into the node's `loading`), and a failure lands in a dismissable line under the tree rather than under the row, since the row's own error is drawn only while it is open and a statement is asked of a closed one as often as not. `Copy` uses `navigator.clipboard.writeText` after the await; Firefox allows that within its transient-activation window, which a metadata query fits inside.

  `DocumentHeader.svelte` sits above the editor carrying the document's name and its menu, and nothing about where it runs. That chip, the data browser's connection, the results pane's `Save` and the top bar's account chip are `Dropdown.svelte`: a chip with a leading icon, a label and a `ChevronDown` that opens a menu whose *contents* the caller supplies as a snippet — a list of actions, a list of choices, a list of file formats — and whose surface and dismissal it does not. Dismissal is the platform's: the menu is a native `popover`, so Escape and a click anywhere else close it, which is what the hand-rolled version was reaching for with a full-window backdrop div and a window keydown handler. The surface itself is `Menu.svelte`, and a `Dropdown` is a chip plus one of those: the inspector's per-field picker needs the same menu with no chip in front of it, and a `Dropdown` per field would stand a popover element behind every row of every selected document for a menu only one of them can ever open. Triggers point a `popovertarget` at the menu they open rather than calling `showPopover` themselves, so moving between two of them — light-dismiss, then re-open — is the browser's ordering and not ours. `Menu` also sizes itself to its contents, because a popover is laid out where it is written and `SplitPane` gives every direct child of a section `width: 100%; height: 100%` — which found the picker the moment a pane rendered a menu beside its own root and stretched it over the window. The top layer also means no pane's overflow can clip a menu, which is why the results pane could not use the absolute positioning the header did — the reason there were two implementations to begin with. A click on any button inside the menu closes it, captured on the way down so the menu is gone before the item's own handler runs (one of them opens a `prompt()`). Open, a chip is accent all through — icon, label, chevron, and a tinted ground — including the bold file chip, whose own colour rule has to stand down while it is open or it silently outranks that. `FileSwitcher.svelte` is the Cmd+P palette that replaced the drawer's file list; the chord is registered both as a monaco action (the editor holds focus and would swallow it) and on `window` (everywhere else, and to keep the browser's print dialog out of it).

### Server-side

- **Hooks** (`src/hooks.server.ts`): `sequence(SecurityHeadersHandler, ProbeHandler, LoggingHandler, SessionHandler, AuthnHandler, AccessHandler)`. Session is an encrypted cookie (AES-GCM via Web Crypto) pointing to a server-side session store.
- **Probes** (`src/lib/server/probes.ts`): `/livez` and `/readyz`, for Kubernetes, answered by a handler in the `sequence` rather than by routes so that a probe is served by as little of the server as possible. It sits *before* `LoggingHandler` and `SessionHandler`: a probe is not traffic (two of them every ten seconds would be most of the request log), and it must not be issued a cookie or have authn read the store on its behalf — for liveness that would make the probe depend on the very thing it must not check. `/livez` consults nothing: liveness failing restarts the pod, and a restart does not bring a session store back, so a store outage failing liveness would turn into the whole fleet restarting in a loop. `/readyz` pings the session store and the file store (`ping`, which the memory stores do not implement and so are always ready; the body reports each under its own name), each under its own 2s deadline so the answer beats a kubelet's default 1s timeout being the thing that decides. It deliberately does *not* check the Trino clusters or the OIDC provider: they are shared by every replica, so failing readiness on them would pull every replica at once and turn "cannot run a query" into "cannot reach the site" for people already signed in. The body names which check failed and nothing more — the cause goes to the log at warn, the same policy as the gate's denial reasons. The paths are fixed and not on the gate's exempt list, because they never reach the gate.
- **Session store** (`src/lib/server/sessionStore.ts`): `session.store.kind` picks `InMemorySessionStore` (the default), `SqliteSessionStore` (one row per session in a file opened through `stores/sqlite/database.ts` below, sealed exactly as Valkey's are and for the same reason — the file is what a volume snapshot copies) or `ValkeySessionStore` (over iovalkey — a fork of ioredis, chosen because it has single, cluster and sentinel in one package and is pure JS, so it bundles into `build/` like everything else; `Bun.RedisClient` does neither). The store contract is `load`/`save`/`destroy` with a TTL, plus an optional `ping` for the readiness probe, and nothing else, which is why the swap is small. One key per session, `keyPrefix + id`, so every operation is single-key and cluster slots never matter. The value is the session document as JSON, **sealed** with a key derived from the store's own `secret` (`Sealer.ts`, the HKDF→AES-GCM that `EncryptedCookie` also uses, under a different `info`) — with the memory store the refresh tokens never left the process, and in Valkey they would otherwise sit in every RDB snapshot and replication stream. This is not a toggle: "store bearer tokens in plaintext" is not a setting anyone should have. The secret is the store's own and not `cookie.secret` reused: the cookie is in every browser and the store is on a host the operator runs, so deriving both keys from one string would make them a single credential that the same leak compromises and that has to be rotated together. A value that will not open is dropped with a warning rather than surfaced, since it is not this user's session whatever it is. The three topologies differ only in the constructor (`stores/valkey/client.ts`, which both Valkey stores open through); `mode` is a required discriminator because zod matches discriminators against the raw input, so a `mode` defaulting to `single` never matches an absent key. Startup pings the store and exits on failure — the same policy as a config that will not validate, for the same reason — and the factory imports the Valkey and sqlite modules lazily so a memory deployment never evaluates iovalkey. `maxRetriesPerRequest: 1` and `commandTimeout` mean a request fails in bounded time during an outage instead of queueing until it ends; a failed `load` rejects through `Session` to a 500, which is fail-closed and the right way round. The client's `error` event has to have a listener or iovalkey prints to stderr itself. What a shared store does **not** fix: `TokenRefreshCoalescer` in `oidc.ts` is per-process, so two replicas can refresh the same refresh token at once, and with Keycloak's *Revoke Refresh Token* on, the loser's request bounces to login and whichever `commit` lands last decides which token the session holds. Sessions are written rarely enough (login, refresh, logout) that this is tolerable; a store-side lock around the refresh is the fix if it is not.
- **File store** (`src/lib/server/fileStore.ts`): `files.store.kind` picks nothing (`browser`, the default: the files stay in localStorage and `/api/workspace` answers 404), `InMemoryFileStore`, `SqliteFileStore` or `ValkeyFileStore`. The contract is `list`/`put`/`remove`/`putUi` per user id plus the optional `ping`/`dispose`, and `put` takes the version it expects and answers a wrong guess with a `conflict` carrying the current record — the compare-and-set is inside the store's transaction, so it is a property of the store and not of whoever calls it. The user id is the partition and is the gate's identity, never anything in the request; a change to what `authn` calls the user is the operator's to deal with, not this code's. The store is a module-level singleton built at import (`fileStore`) because the routes need it and there is no way to hand them what the hook built, and `hooks.server.ts` imports it for the readiness ping and shutdown. Files are **not** sealed, in any store: the SQL text is what a copy of the store is restored for. The routes are `src/routes/api/workspace/` (`GET` the listing, `PUT`/`DELETE` a file, `PUT` the ui record), under the default-deny gate with nothing exempted, always answering JSON, with the body validated by zod in `workspaceApi.ts` (ids must be UUIDs, so a key is never a client's choice of length) and capped at `files.maxBytes` — which defaults to adapter-node's own `BODY_SIZE_LIMIT` because the adapter fails the body *stream* past its limit, which reaches the route as a rejected `text()` and has to be caught to be a 413 instead of a 500. A `PUT` with neither `If-Match` nor `If-None-Match: *` is a 428: an unconditional write is the thing the versions exist to rule out.

  **`stores/sqlite/database.ts`** is what both sqlite stores open through, and the order of its pragmas is the point: `locking_mode = EXCLUSIVE` *before* `journal_mode = WAL` makes the connection hold the file's lock for good and never use shared memory, so a second process — a second replica on a shared volume — fails on its first read with "database is locked" rather than sharing a file sqlite cannot share over a network filesystem. `migrate` runs numbered steps against `PRAGMA user_version`, each in its own transaction, which is the first persistent schema this app has and so the first place a code change can break existing data. `bun:sqlite` is the runtime's own module: it is in `ssr.external` in `vite.config.ts`, and adapter-node's rollup then reports it as an external it could not resolve, which is the intended outcome and not a warning to fix. Both stores are imported lazily by their factories so a `browser`/`memory` deployment — and `vite dev` under node — never evaluates them.

- **Authn** (who): Pluggable — `NoAuthn` (dev) or OIDC with PKCE, token refresh via priority queue. Either way it yields one thing: an `Identity` (`src/lib/server/identity.ts`) on `event.locals.identity`, a `userId` plus the `claims` the mechanism was able to say about the user. Absent means signed out. Only the `userId` is sent to the browser in layout data — nothing on the client reads a claim, and shipping a whole token payload to the page would be exposure bought for nothing. `claimsFrom` picks which OIDC token the claims come from: `id_token` (the default; it *is* the statement of who the user is) or `access_token`, which exists because Keycloak puts client roles in the access token unless someone ticks "Add to ID token" on the client roles mapper — so a role rule usually wants the other token. The access token is read with an unverified JWT decode, which is safe only because it came back over TLS from the provider's own token endpoint in a call we made: there is no untrusted party in between whose signature there would be anything to check. `authn: none` takes a literal `claims` map, which is the only way to exercise an authz rule without standing up an identity provider. **Signing out is RP-initiated**: dropping our own session is only half of it, because the provider keeps its own SSO cookie and answers the next visit to the login path without a prompt — the same person comes straight back, which makes the sign-out button on the forbidden page (where it is the *only* move a refused user has) a lie. So logout revokes the refresh token, destroys the session, then hands the user to the provider's `end_session_endpoint` with an `id_token_hint` — which is the only reason the raw `id_token` is kept in the session at all. `post_logout_redirect_uri` is `ORIGIN + "/"` and has to be registered with the provider (in Keycloak: the client's "Valid post logout redirect URIs"). A provider advertising no `end_session_endpoint` gets a warning at startup and a plain redirect home. The path to POST to reaches the browser as `logoutPath` in layout data beside the `userId`, which is what puts `Sign out` in the account menu; it is absent under `authn: none`, so the item is simply not drawn rather than offering a way out of a session no provider opened.
- **Authz** (whether) and the access gate: Authz is configured separately from authn and reads nothing but the identity's claims — that separation is the point: a rule never learns which provider issued the identity, and a mechanism never learns what a rule will look for. Three authorizers: `allow` (the default when `authz` is absent), `cel`, and `require-keycloak-client-role`. **`cel`** (`celAuthz.ts`, over `@marcbachmann/cel-js` — zero dependencies, so it bundles like everything else) is a CEL expression over two variables, `claims` and `userId`, and is the kind a policy gets when it names none (`authz: { expression: "..." }`) — put in by a `z.preprocess` on `AuthzSchema`, since zod matches a discriminator against the raw input and a defaulted literal never matches an absent key. The claims are *one* `claims` map and not a variable each, because `has()` only works on a field selection (`has(claims.groups)` is expressible, `has(groups)` is not) and because a claim can then never collide with a CEL keyword. Both of its decisions fail closed: only exactly `true` allows, and an evaluation error refuses — CEL makes a missing map key an error, so a rule about `resource_access.finance` refuses a user who has no such key rather than accidentally passing them. What can be known at startup is checked there and exits the process like any other bad config: syntax, a variable that is not one of the two, and — from the checker's inferred type — an expression that can never be a boolean; a bare claim checks as `dyn` and is judged at runtime. **`require-keycloak-client-role`** is sugar for the expression `"<role>" in claims.resource_access.<client>.roles` (`RequireKeycloakClientRole`, beside `CelAuthorizer`), and is *built as one* — its `name` is that expression, so the startup log says what is actually checked — rather than a second authorizer with its own rules for what refuses. It is a kind of its own only because `client` defaults to this app's `clientId`, since "the role I granted Trinocular" means the roles of the client Trinocular signs in as, and no expression can name that. A clientId is free text and `com.example.app` is an ordinary one, so the client is written as a field selection only when it is identifier-shaped and not a CEL reserved word, and as `["com.example.app"]` otherwise — interpolated into a dotted path it would read as three levels and refuse a user who does hold the role, the same shape of bug as reading a tree node's kind back out of a dotted id in the schema browser. Roles laid out any other way (`realm_access.roles`, `groups`) are an expression; the `claim` escape hatch the old `require-role` carried for them is gone with it. A misconfigured rule with no client to default to exits at startup rather than locking everyone out at runtime.

- **Per-connection authz** (`src/lib/server/connectionAuthz.ts`): a connection may carry an `authz` block of its own, and it is the *same* vocabulary — the schema is literally the same `AuthzSchema`, and `createAuthorizer` builds both — because `Authorizer` reads nothing but claims and so was already connection-agnostic. A connection rule **narrows and never widens**: the application-wide gate has already run in `AccessHandler` before anything here is consulted, so adding a rule to a connection can lock people out of that cluster but can never let somebody past the front door. That direction is the safety property, and it is why a connection with no `authz` adds no condition rather than inheriting one — the top-level policy applied either way. Enforcement is in the **proxy route**, because the hook sequence runs before routing and has no connection id to judge; `+layout.server.ts` filters the list it hands the browser through the same predicate, since offering a cluster that answers 403 is a menu of traps — and worse than cosmetic, because `Workspace` heals a stored connection the list does not hold to the *first* connection in the list, so a forbidden one being listed could become the default the whole workspace aimed at. The list is a menu, not a lock: the proxy takes its id from the URL and checks again. An id the config does not declare is refused rather than treated as unconstrained, so a typo cannot be the way past every rule. `hooks.server.ts` calls `logConnectionAuthz()` at startup for its side effect as much as its log line — nothing else imports the module except two lazily-loaded route modules, so without that call the authorizers would be built on whichever request first touched one, and a policy that cannot be built would take the process down mid-request instead of refusing to start.
- **`AccessHandler`** (`src/lib/server/authz.ts`) is where *both* halves are enforced, last in the `sequence`, so the OIDC handler has already dealt with logout/callback/login itself and a refused user can still sign out. Signed out and refused are the same kind of decision and belong in one place: the authn half used to be a redirect in `+layout.server.ts`, but a layout only guards what renders under it, so an API route added later inherited nothing and served anonymous traffic until somebody wrote its own check (which is what the Trino proxy's hand-rolled 401 was). Default-deny with a named exempt list is the only arrangement where forgetting is safe. A navigation gets a page — `/auth/login?returnTo=…` signed out, `/auth/forbidden` refused — and anything else gets JSON with a status, because a thrown SvelteKit error renders the fallback HTML page even for a JSON caller and the Trino client would meet that as a parse failure rather than a 403. `returnTo` has to strip `/__data.json` and `x-sveltekit-invalidated` from a data request: in a hook `event.url` is the literal request, not the logical page a load function would have seen. The exempt list covers the fixed `/auth/*` routes *and* the configured `paths.prefix`, since the auth pages are SvelteKit routes that do not move with the prefix — exempting only the prefix would make a renamed deployment refuse its own forbidden page, which is a redirect loop rather than an explanation. A denial's reason goes to the log only: it names claims the user cannot change and would tell an attacker which role to go and ask for.
- **Proxy** (`src/routes/api/trino/[id]/[...path]/+server.ts`): Forwards requests to configured Trino connections, rewrites `nextUri`/`partialCancelUri` in responses to route back through the proxy. Sets `X-Trino-User` from the gate's identity and the bearer token from the session. The `X-Trino-*` headers it forwards *from* the browser are a list, not the prefix match the response direction uses: `X-Trino-Authorization-User` and `X-Trino-Original-User` are Trino's impersonation headers, `X-Trino-Role` picks a role inside a catalog's access control, and `X-Trino-Extra-Credential` hands credentials to connectors — forwarding those while overriding `X-Trino-User` would settle who you are and then let the request say who to act as. Only session shape travels (source, catalog, schema, session, prepared-statement); a header the client learns to send has to be added to the list too. The response direction stays a prefix match because that is the cluster talking back, and the client needs all of it to stay in step — but it is an allowlist on *every* path out, error responses included. It used to be applied only to the 200/JSON path, and an upstream 401 therefore passed its headers through verbatim: whatever answers at the connection URI is not necessarily Trino, and a `Set-Cookie` from it lands on this app's origin, which is session fixation handed over by the proxy.

  Two things decide where a proxied request goes, and **both** are checked against the URL after parsing, never against the raw route parameter. The path, because SvelteKit decodes a rest param once and a double-encoded traversal (`%252e%252e`) arrives as literal `%2e%2e` that only `new URL` normalises. And the origin, because a parameter beginning with `/` makes `"/" + path` protocol-relative: `//evil.example/v1/statement` resolves to a different *host* while `pathname` stays `/v1/statement`, so a path-only allowlist waves it through and the request carries `X-Trino-User` and the user's bearer token off to that host — reachable from a plain link, since a top-level GET navigation sends a `SameSite=Lax` cookie. Checking one without the other checks the half that was never in doubt.
- **CSP** (`svelte.config.ts`): the app draws whatever a cluster returns, so the point of a policy is that a string arriving in a result cell can never become script. `mode: "auto"` lets Kit hash its own inline bootstrap, so `script-src` needs nothing loosened. The two directives that are not defaults are Monaco's: `style-src` takes `'unsafe-inline'` because Monaco writes a `<style>` element for its theme at runtime and sets `style=""` on every line it renders — neither can be hashed ahead of time, and without it the editor renders as unstyled text — and `worker-src` takes `blob:` alongside `'self'` for the fallback vite uses where a browser will not take a module worker. It is verified by loading the built app in headless Chromium and asserting zero violations while the editor boots and a query runs, which is the only way to find out: a CSP that is too tight fails silently in the console rather than at build time.

- **Logging and errors** (`src/lib/server/logging.ts`, `handleError` in `hooks.server.ts`): the level comes from `LOG_LEVEL` in the environment, not the config file — it has to apply before the config is read, since loading the config is itself worth logging including the failures that exit, and it is the setting an operator wants to raise on a running deployment without editing the file that holds the security policy. `info` by default; an unrecognised value warns and falls back rather than letting pino throw and stop the server over a typo. **Severity comes from the status, in two places, because a route's exception never reaches the request hook's `catch`** — SvelteKit catches it inside `resolve`, hands it to `handleError`, and returns a 500, so from the hook a crashed endpoint looks like a served page but for its status. `handleError` logs 5xx at error and everything else at warn (it fires for a plain 404 too, and "no such route" at error level would bury real failures under bot traffic), and the request-completed line logs 5xx at error for the same reason. The body `handleError` returns carries the request id and nothing more: the message and stack are for the log, and the id is what lets somebody quoting an error be found in it.

- **Security headers** (`src/lib/server/securityHeaders.ts`): `nosniff` and `Referrer-Policy: same-origin`, first in the `sequence` so they reach every response the rest of the chain returns, refusals included. `nosniff` earns its place here because the proxy streams an upstream body through with the cluster's own `content-type`. Clickjacking is already covered by the CSP's `frame-ancestors 'none'`, which is what a browser consults when both it and `X-Frame-Options` are present. A thrown redirect is the exception: it propagates past the handler for SvelteKit to turn into a response, so a 303 goes out without them — nothing there to sniff or leak.

- **Config** (`src/lib/server/config.ts`): Zod-validated config loaded from `TRINOCULAR_CONFIG` env var (a JSON or YAML file path — YAML goes through `Bun.YAML`, so it needs the bun runtime). Defines branding, connections, session settings, the file store, and the authn and authz modes. A validation failure exits the process: a server that came up with half a policy would be worse than one that did not come up.

  **`TRINO_URL`** is the whole configuration for somebody who just wants to look at the thing: the existing no-config defaults (`authn: none` as `alice`, a cookie secret made fresh each start, sessions in memory) plus one connection named after the URL's host, run through the same `ConfigSchema` so a URL that will not parse is reported the same way a file's would be. It is read only when `TRINOCULAR_CONFIG` is unset and the two together are a startup error, because the alternative is inventing a precedence rule for a shortcut whose whole value is that there is nothing to reason about. It is also why `DEFAULT_CONFIG` now pins `cookie.secure` rather than leaving it to `hooks.server.ts`: the derivation there defaults an absent `ORIGIN` to *true*, which is right for a deployment and wrong for the one case that by definition has not been deployed — a `Secure` cookie is never sent back over plain http, so the session would be reissued on every request. `demo/compose.yaml` is the same variable one layer out: Trino carries `profiles: ["${TRINO_URL:+external}"]`, which is empty (and so no profile at all) when the variable is unset and an unactivated profile when it is set, so one file both bundles a cluster and stays out of the way of yours — with `depends_on: … required: false` for the half where the dependency is not there to wait for.

  ```yaml
  authn:
    kind: oidc
    issuer: https://keycloak.example/realms/prod
    clientId: trinocular
    clientSecret: ...
    scope: openid profile email
    claimsFrom: access_token   # where Keycloak puts client roles by default

  authz:
    kind: require-keycloak-client-role
    role: user                 # "user" in claims.resource_access.trinocular.roles

  connections:
    warehouse:
      name: Warehouse
      uri: https://trino.example:8443
    finance:
      name: Finance
      uri: https://trino-finance.example:8443
      authz:                   # on top of the rule above, never instead of it
        expression: '"finance" in claims.groups'
  ```

### Monaco language package

`packages/monaco-language-trino/` is a bun workspace package providing Trino SQL support: ANTLR-generated parser (SqlBase.g4), completion, semantic tokens, diagnostics, folding, and statement splitting. Imported as `monaco-language-trino`.

**The app consumes this package's TypeScript source, not a build.** Its `exports` point at `src/index.ts`, the workspace makes `node_modules/monaco-language-trino` a symlink to `packages/`, and `optimizeDeps.exclude` in `vite.config.ts` keeps vite from pre-bundling it. So an edit under `packages/` is live immediately — no `build:lib`, no `bun install`, no clearing `node_modules/.vite`. Each of those was previously a way for the running app to silently keep executing stale code, which is easy to miss because the app fails by rendering nothing rather than erroring. `bun run check` now type-checks the package source along with the app, so drift shows up there too.

`build:lib` still exists for publishing the package standalone, but nothing in this repo consumes `dist/`. `build:grammar` regenerates the parser and then runs `fix:generated`, which restores the type-only `ParseTreeListener` import that the app's `verbatimModuleSyntax` requires and antlr-ng does not emit.

### Dependencies and the image

**Everything is a `devDependency` except `monaco-editor`, and that is load-bearing.** adapter-node bundles the vite output so that "deployments only need their production dependencies": it passes `Object.keys(pkg.dependencies)` to rollup as `external` and bundles everything else. The image ships `build/` alone — adapter-node's output, no `node_modules` — so anything left in `dependencies` becomes a bare import in `build/server/` with nothing to resolve it. Bun does not fail on that; it goes to the network and installs the package at boot, ignoring `bun.lock`, which is how the image came up running a zod the lockfile had never pinned. Run the image with `--network none` and it says what is really going on: `Cannot find package 'zod'`. So a new runtime import belongs in `devDependencies` — the name is wrong for what it does here, but it is the switch adapter-node reads.

`monaco-editor` stays in `dependencies` because it cannot be bundled and does not need to be. Its modules import `.css`, which adapter-node's rollup has no loader for, so bundling it fails the build outright; pulling it in through vite instead (`ssr.noExternal`) works but adds ~26 MB of dead weight. Dead because `+page.ts` sets `ssr = false`: the page component's server chunk is emitted and never evaluated, so the bare `monaco-editor/editor/...` imports in it are never followed. What the editor needs, it needs in the browser, where the client build has it bundled already.

**Monaco's deep imports** (`monacoSetup.ts`, the hand-picked feature list behind the `monaco-editor` alias in `vite.config.ts`) are spelled `monaco-editor/<path under esm/vs>`: since 0.56 the package has an `exports` map, `./*.js` → `./esm/vs/*.js`, and the old `monaco-editor/esm/vs/...` spelling resolves to nothing. The map only ever adds `.js`, so the one stylesheet — the codicon font — cannot be named through it and is taken through `monaco-editor/features/codicon/register.js`, the package's own one-line module that imports it. The other `features/*/register.js` entries are the supported way to pick features, but they are not one-for-one with what `editor.main.js` loads (its `suggest` is `suggestInlineCompletions`, not `suggestController`; `semanticTokens` is the viewport half only), so the list here still names the contrib modules `editor.main.js` itself names.

**What a build is called** (`src/lib/build.ts`, `define` in `vite.config.ts`): the version and the commit are *inputs* to the build — `TRINOCULAR_VERSION` and `TRINOCULAR_COMMIT` in the environment of `vite build`, which the Dockerfile takes as build args of the same names — and never something the build computes, because the image's build context has no `.git` to ask (the `.dockerignore` allowlist) and a number that needs history to count needs a full clone to count it. CI passes `MAJOR.MINOR.<run number>`, with `MAJOR.MINOR` read off `package.json`'s `version` (whose patch digit means nothing) and the number from `github.run_number`, which is per workflow file and consumed by pull-request runs too, so main's numbers have gaps and are still unique and increasing, which is all a build number is for. A build told nothing is `0.0.0`; the commit falls back to `git rev-parse HEAD` where there is a repository to ask, so a laptop's `bun run build` still knows what it built. `docker/metadata-action` turns the one version into the tags, the labels and the manifest/index annotations, with `org.opencontainers.image.version` overridden to the bare version for both variants — left to the action, the distroless image's would be its top tag, `0.1.212-distroless`. The value reaches the code as `__TRINOCULAR_BUILD__`, a vite `define` and so a string in both bundles, and is read nowhere but `$lib/build`: the first log line (`logging.ts`, which is the first module the server evaluates), the wordmark's tooltip, and the foot of the account menu, where the commit links to `homepage` in `package.json`. Not `/readyz`: it answers without a session, and the pattern here is to tell anonymous callers nothing they do not need.

**`typescript` is held at 6.x on purpose.** 7.0 is the Go compiler — platform binaries and no JS API — and svelte-check and the kit plugin drive the compiler through that API (`typescript: ^5 || ^6` in their peer ranges), so `bun update --latest` will offer 7 and it will not work. 6.0 changed two defaults that the tsconfigs now set explicitly: `types` is `[]` rather than every `@types/*`, which is why `tsconfig.json` names `bun` (it was `Cannot find module 'bun:sqlite'` across the server until it did), and `rootDir` is the tsconfig's directory rather than the sources' common root, which is why `tsconfig.lib.json` in the language package says `src` (without it the `.d.ts` landed in `dist/src/`, and TS 6 refuses the ambiguity outright). `esModuleInterop` is always on and setting it `false` is an error.

## Key conventions

- **Svelte 5 runes** throughout: `$state`, `$state.raw`, `$derived`, `$derived.by`, `$effect`, `$bindable`. No stores.
- **Snippets** for component composition (table cell renderers, split pane slots).
- Large/frequently-updated data (`Result.data`, `Result.columns`, `Result.stats`) must use `$state.raw()`, not `$state()`, to avoid proxy overhead. `$state.raw` compares by reference, so anything accumulating into one of these has to hand back a new value — see `Rows` for what that costs when the new value is built by copying.
- **Nothing holding runes may be constructed inside a `$derived` or an `$effect`.** Svelte does not register a dependency on a source created by the reaction currently running (`current_sources` in its runtime): from the reaction's point of view it is producing that value, not observing it, so there is nothing to notify. A reaction that both builds an object and reads its state therefore reads it exactly once, forever. It fails silently and it fails *intermittently* — the object is only born inside a reaction the first time, so the same code works on every later visit, which reads as a loading race rather than a missing subscription. Build such things where the reaction can only find them already made: `Workspace.#catalogs` is why this is written down.
- **The design system lives in `src/style.css`** and is deliberately small: two text sizes (`--text` 13/20, `--text-sm` 11/16), four heights (`--h-rail` 36, `--h-row` 30, `--h-tree` 26, `--h-ctl` 24), three radii (`--r-panel` 8, `--r` 6, `--r-kbd` 4), one icon size (14px, 12px for chevrons), and one accent with four jobs — selection, focus, the running statement, links. Spacing is used literally on a 6/8/12/16 scale rather than tokenised. Surfaces are a monotonic ramp `--s0`..`--s3` plus `--line`/`--line-strong`, and text is `--fg`/`--fg-2`/`--fg-3`; the ramp means the same thing in both themes, which the old `--bg-1`/`--bg-2` and `--border`/`--border-dark` pairs did not — each swapped which one was stronger when the theme flipped. `data-theme` on `<html>` picks the palette, from `src/lib/theme.svelte.ts` — a three-way choice (`system`/`light`/`dark`) rather than a toggle, offered in the account menu. The toggle it replaces latched a `manualOverride` flag on its first click and never followed `prefers-color-scheme` again for the rest of the session, so "back to whatever the OS says" was the one position it could not reach. An explicit choice is remembered under `trinocular:theme`; `system` is the absence of a preference and so is stored as the absence of the key. The global primitives are shared rather than re-declared per component: `.rail` (and `.rail > svg`, muted), `.chip`, `.menu` (with `.menu .selected` for the current choice), `.fill` for the flex filler every rail has, `.small` for the small size on its own and `.meta` for small-and-muted, `.muted`, `.warn`, `.link` for a button that reads as a link, `.dot`, `.ell`, `.mono`, `kbd`, and `.textbox` for a text input that stands on its own — a bare `input[type="text"]` is unstyled, since most of them sit in a box that draws the border (the filter box, the file switcher) and each used to undress the input the stylesheet had dressed. `.menu` is the surface and rows of a dropdown, with placement left to `Dropdown.svelte`, which is what opens every one of them. The two things still outside the system on purpose: the tree's 20px reload and menu buttons (a 24px `.chip.square` overfills a 26px row), and the 12px icons on small buttons, which the "one icon size" rule does not name.
- Formatting: 2-space indent, double quotes, no trailing commas, 100-char line width — `.prettierrc`, applied by `bun run format` to the app and the language package alike (`.prettierignore` keeps the generated parser and the prose out of it).


# MCP

You are able to use the Svelte MCP server, where you have access to comprehensive Svelte 5 and SvelteKit documentation. Here's how to use the available tools effectively:

## Available Svelte MCP Tools:

### 1. list-sections

Use this FIRST to discover all available documentation sections. Returns a structured list with titles, use_cases, and paths.
When asked about Svelte or SvelteKit topics, ALWAYS use this tool at the start of the chat to find relevant sections.

### 2. get-documentation

Retrieves full documentation content for specific sections. Accepts single or multiple sections.
After calling the list-sections tool, you MUST analyze the returned documentation sections (especially the use_cases field) and then use the get-documentation tool to fetch ALL documentation sections that are relevant for the user's task.

### 3. svelte-autofixer

Analyzes Svelte code and returns issues and suggestions.
You MUST use this tool whenever writing Svelte code before sending it to the user. Keep calling it until no issues or suggestions are returned.

### 4. playground-link

Generates a Svelte Playground link with the provided code.
After completing the code, ask the user if they want a playground link. Only call this tool after user confirmation and NEVER if code was written to files in their project.
